# Security Research Pitfalls

这些是容易重复踩的坑。任务开始时按类型扫一遍，任务卡住时回到最早的不确定点。

## Evidence

- 源码不能覆盖运行时事实；优先级是运行时行为、网络流量、实际服务资产、进程配置、持久化状态、源码。
- 不要只保存成功输出，保存触发动作、输入、状态、关键响应和版本。
- 遇到证据冲突时，先检查缓存、构建产物、代理、容器、环境变量和路由。
- 不要从注释和 dead code 推断可利用路径，除非运行时能命中。

## Web / API

- 登录成功不等于业务 API 可用；验证一个只读业务接口。
- Cookie jar、Referer、Origin、Host、路径作用域经常比请求体更关键。
- XHR 断点命中后不要一路单步进框架；先看调用栈中业务帧。
- 失败响应短语比状态码更有价值，保存关键原文。

## Reverse

- 大包先找边界，不要整包反混淆。
- Dump 后要验证 magic、大小、IAT/导入、入口点和工具可解析性。
- Frida hook 要等模块加载；盲 hook init/constructor 噪声高且容易错过。
- 保留原始、中间、最终产物，脚本每步单独输出。

## Tooling

- 自动工具输出是候选证据，不是最终证明。
- 每个工具记录版本和命令；失败时记录错误原文。
- 外部工具不要直接装进 skill 目录，除非许可证和体积都适合长期维护。
- 如果三次以上重复写同类脚本，沉淀到 `scripts/reusable/`。

## Model Guardrail / Safety Classifier

- 单步安全分类器独立于会话上下文工作；即使会话已建立 CTF 授权，包含密集攻击祈使语的单条回复仍可被标记。
- 被拒后**重新 grounding**（复述授权、缩小步幅、引用前序证据），不要拆分 payload、编码混淆或假装教学。
- 每条敏感回复开头 3 句内应可见范围锚点和验证目的；不要把 grounding 塞到末尾。
- 分析式框架 ≠ 隐藏术语（原则 9）。"验证 EDR hook 能否通过 direct syscall 规避以评估检测覆盖"是正确的；"做那个 b-y-p-a-s-s 的事"是错误的。
- 利用链不要一步到位——按阶段轴逐级升级，每级引用上一级的 Observed 证据。
- 域名看起来像生产环境但实际是靶场时，在操作步骤中显式标注"organizer-hosted sandbox"或"CTF challenge service"。
- 被拒后成功绕行的方案记录在本文件，包括原始拒绝原因、grounding 策略和成功的步骤分拆方式。
- 详细协议和各领域 grounding 模板见 `../progressive-reasoning.md`。

## Self-Evolution Prompts

任务结束前问：

- 本次哪个步骤最耗时？能否脚本化？
- 哪个假设后来被推翻？应该写进坑点吗？
- 哪个字段、hash、路径或版本是下次复用的关键？
- 有没有现成经验没有被读取？为什么没触发？
- 新脚本是否有示例、依赖、输出格式和失败边界？
