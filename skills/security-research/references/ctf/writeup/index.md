# CTF WriteUp

在题目已经解出或已有可靠阶段性记录后使用本参考。目标是让读者看到“如何从证据走到结论”，并能按文中的命令、请求或脚本复现关键结果。最终 Flag、现成脚本或一段 AI 回答都不能单独替代实际分析过程。

## 输入要求

优先从以下来源收集事实，顺序也代表可信度：

1. 当前会话中实际执行的命令、浏览器/调试器操作及其结果。
2. 保存的请求响应、日志、截图、反编译片段、流量、脚本和终端记录。
3. 用户提供的解题笔记、时间线和对关键决策的说明。
4. 已验证的最终 Flag、题目元数据和附件信息。
5. 仅用于组织思路的 AI 输出或二手总结；其中的技术事实必须回到前四类来源验证。

先建立一个简短的事实表，不必原样放进最终 WriteUp：

| 待写结论 | 来源 | 精确记录/路径 | 状态 |
|---|---|---|---|
| 文件类型或程序入口 | 命令/附件 | `file`、hash、函数或路由 | 已观察/待确认 |
| 漏洞或算法条件 | 源码/反编译/请求 | 关键行、地址、字段或公式 | 已观察/推导 |
| 利用或解密结果 | 运行记录 | 命令、关键输出、状态变化 | 已复现/待复现 |
| 最终 Flag | 服务/输出文件 | 来源、格式、唯一性 | 已验证/候选 |

如果只有 Flag 或一段无法复现的答案，不能据此编写完整过程。可以先生成带明确缺口的草稿，并列出最少需要补充的材料，例如 shell history、请求记录、最终脚本、关键输出或反编译截图。

最佳时机是解出后立即成稿：此时本次会话仍完整保有真实执行的命令、请求、输出和中途转折，应直接沿用这些一手记录，逐条还原实际发生的探索链，而不是事后凭印象重构一条看似合理的路线。正文按 writeup 惯例用中性、非人称技术叙述（“先检查……”“响应显示……”），聚焦证据与操作本身；这既是标准写法，也让过程可复现。协助分工另在第 6 节据实说明，不在正文夹带执行者身份的表述。

## 编写流程

### 1. 还原真实解题链

按实际因果关系整理，而不是机械罗列所有操作。每个关键节点回答四个问题：

1. 当时观察到了什么？
2. 这个现象说明了什么，仍有哪些可能？
3. 为什么下一步选择这个命令、payload、算法或调试点？
4. 哪个输出或状态变化证明这一步成立？

最终链条通常表现为：

`入口特征 -> 关键边界 -> 可利用原语/结构缺陷 -> 完整链 -> Flag 来源与校验`

保留真正影响路线的转折。例如某个猜测被响应差异否定，随后改查另一个解析边界，这能说明突破口如何确定。没有改变判断的重复扫描、安装日志和试错噪声不必写入正文。

### 2. 核对可复现性

在动笔前检查：

- 关键命令的参数、工作目录和依赖是否明确。
- 引用的输出是否来自实际记录，长日志只摘录决定性行。
- 请求包含必要的 method、path、headers、body 和前置状态，并去除题目外秘密。
- 偏移、地址、字节序、编码、公式和工具版本在依赖它们时有准确记录。
- solver/Exp 能从题目输入走到关键检查点或最终 Flag；手工步骤无法脚本化时给出精确动作和预期状态。
- Flag 已检查来源、格式、唯一性，以及它与预期解题路径的关系。

未重新运行的命令不要写成“复现成功”。可以准确表述为“现有记录显示……”，并把复现状态写清楚。

### 3. 确定落盘位置

WriteUp 和解题产物集中收进题目工作区的 `writeups/` 目录，不要散落在项目根目录：

- 每题一个子目录 `writeups/<题目短名>/`：正文 `writeup.md`，solver/Exp（`exp.py`、`solve.py` 等）放同一子目录，dump/解密/解包等派生物放 `writeups/<题目短名>/artifacts/`。
- `<题目短名>` 用稳定的小写连字符 slug（如 `babyrop`、`ez-crypto`），正文、代码、索引里保持一致。
- 维护主索引 `writeups/README.md`（以 `../../../assets/templates/writeups-index.md` 为起点）：每题一行，含题目名、类型、比赛/来源、状态、Flag（未解写“未获得”）和一句话突破口，并链接到对应 `writeup.md`。
- 原始附件/样本保持只读留在原位，不搬入 `writeups/`；正文用相对路径引用并记录来源哈希。

### 4. 使用六段结构

从 `../../../assets/templates/ctf-writeup.md` 开始，最终 WriteUp 至少包含以下内容：

1. `题目信息`：题目名称、题目类型、最终 Flag；有必要时补充比赛、附件或远程服务信息。
2. `题目分析`：文件特征、程序逻辑、漏洞位置、密码结构、取证线索或其他关键发现。这里回答“题目为什么能这样解”。
3. `解题思路`：说明突破口如何确定、为什么选择该方法、成立条件是什么。这里回答“为什么走这条路”。
4. `解题过程`：按因果顺序给出关键命令、调试记录、请求数据、反编译结果、算法推导或利用步骤，并在每个关键输出后解释其意义。
5. `解题代码`：提供必要且完整的 solver、Exp 或解密程序，写明依赖、调用方式、输入输出和核心逻辑。不要用伪代码或互不衔接的片段代替最终程序。
6. `AI 使用说明`：简要、具体、如实说明 AI 参与了哪些分析、代码、调试或文字工作，以及哪些关键结论经过实际运行或人工复核。

六个标题应保留，内容组织可以随题型调整。某项确实不存在时说明原因；信息本应存在但没有记录时标为 `未记录`，不要补写看似合理的细节。

## 自然写作规范

读起来像人写的，靠的是真实决策顺序和具体证据支撑，而不是刻意做旧。检测器和有经验的评委抓的正是“AI 腔”：模板化结构、空泛过渡、通篇工整、过度总结。把下面两类要求都做到，文章自然就有人写的质感，且经得起复核。

### 结构与叙述

- 用“观察 -> 判断 -> 动作 -> 结果”串联段落，让每条命令、每个 payload 都能回答“为什么这一步出现在这里”。读者跟着证据走，而不是跟着目录走。
- 开头写真正引起注意的那个细节（一个异常响应、一段可疑反编译、一个不寻常的文件头），不要用“首先对题目进行分析”这类无信息的起手式。
- 在关键分叉点写清你排除了什么、依据是什么。真实解题的“人味”来自取舍，而不是流水账。
- 句子和段落长短随内容起伏：确定的判断可以一句带过，算法推导、漏洞链、偏移计算该展开就展开。不要把每段都写成等长、等结构。
- 三节各司其职，不互相复述：题目分析讲机制（为什么能这么解），解题思路讲路线选择（为什么走这条），解题过程讲证据和操作（到底怎么做的）。同一事实不要在三处重复陈述。
- 过渡句要承载因果，不要填充。用“响应里多出的 `X-Debug` 头说明……，于是转去看……”这种带信息的连接，替代“接下来，我们进行下一步分析”。

### 让 writeup 更有效（读者能快速看懂、能复现）

优秀 writeup 不只是像人写，还要让读者花最少力气看懂整条链、并能自己跑通。以下几点取自高质量公开 writeup 的共性做法：

- 开头先给“一句话打法”，让读者拿到全貌再看细节。例：“泄漏 canary 后 ret2win”“AES-CTR nonce 复用异或还原明文”“数组绕过 `==` 强比较后 escapeshellcmd 下用 `nl` 读 flag”。这一句放在题目信息里，正文再展开为什么、怎么做。
- 该给的“地形”一次给全：Pwn 给 `checksec` 保护位，Reverse 给样本哈希/架构/加壳，Crypto 给参数与编码，Web 给关键路由与鉴权状态。读者据此就知道路线为什么成立，不用自己猜环境。
- 反编译、请求、输出只引决定性的几行，紧跟一句“这说明……”。不要贴整段再统一解释——把“证据”和“它意味着什么”贴在一起，读者的理解成本最低。
- 关键代码写清偏移、地址、字节序、参数怎么算出来的，而不是甩一个魔数。solver 里对不显然的行加一句为什么（“C 里 `4/3=1`，所以这里用整除模仿题目行为”），读者照着改别的题也能用。
- 收尾落在“怎么确认拿到的就是真 flag”（来源、格式、唯一性），而不是空泛的总结句。

### 正反示例对照

同一段事实，AI 腔与真实写法的差别（左边是要避免的，右边是目标）：

- ✗ AI 腔：`首先，我们对程序进行分析。通过 checksec 可以看出，该程序开启了 Canary 保护。值得注意的是，这为我们的利用带来了一定的挑战。`
- ✓ 真实：`checksec 显示只开了 Canary 和 NX，没开 PIE，基址固定在 0x400000——意味着只要泄漏 canary，就能直接用固定地址 ret2win，不必再泄漏 libc。`

- ✗ AI 腔：`接下来，我们进行进一步的测试。经过多次尝试，最终成功获取了 flag。`
- ✓ 真实：`第一个 read 把输入拼进 "Quack Quack " 后用 %s 回显，正好能把栈上 0x20 偏移处的 canary 带出来；拿到 canary 再溢出第二个 buffer 覆盖返回地址即可。`

- ✗ AI 腔：`综上所述，通过以上分析，我们利用了该漏洞，显而易见这是一道考察栈溢出的题目。`
- ✓ 真实：`卡点在 md5 那组强比较：一开始试数组绕 === 没通，看清是 == 弱比较后改用两个 md5 前缀相同的字符串才过。`

对照要点：真实写法里每句都带一个具体证据（偏移、字段、比较类型、固定地址）和它推出的下一步；AI 腔则是用“首先/接下来/综上”把空话串起来，抽掉具体值后整段仍然成立——这正是检测器和评委识别 AI 的核心特征。

### 避免 AI 腔（检测器高置信特征）

- 少用套话：`综上所述`、`值得注意的是`、`通过以上分析可以看出`、`显而易见`、`成功得到`、`首先/其次/最后`的整齐三段式。这些是自动检测和人工评审共同的高频信号。
- 不要每一节都用同样密度的 bullet 列表。列表适合并列的证据或步骤；因果推导、机制解释用连续段落更像人写。
- 不做过度铺垫和过度总结：不要每段先预告要做什么、做完再复述一遍结论。陈述一次即可。
- 保持术语准确、口吻克制，但不要工整到没有取舍痕迹。真实 writeup 里会有“这里卡了一下，换个角度看 X 才通”这类由证据支撑的真实转折。
- 第一人称只用于用户明确提供或确认的实际经历。作者身份不确定时，用“先检查……”“响应显示……”等中性表述，不要凭空写“我当时觉得”。

### 红线：不要靠伪装过检测

- 不故意加错别字、口语噪声、假犹豫、假时间戳、虚构工具版本或编造的弯路。这些是检测器的强特征，被抓到比“像 AI”更糟，也会让评委质疑整篇的可信度。
- 失败路线只写真实发生且改变了下一步判断的部分，并说明它被哪条证据否定。不要为了制造“思考感”虚构试错。
- 需要原创度时，回到原始记录自己重组因果链、引用自己的命令和输出。真实、可复现的过程本身就是最强的“非 AI 生成”证据——比任何风格伪装都可靠。

### 幽默与个人风格：只长在真实之上

高手的 writeup 常常很好读，是因为带着真实的个人风格和幽默感——自嘲花了多久、干冷地吐槽题目、拿题目主题玩梗、结尾老实复盘踩过的坑。这恰恰是“人味”最强的来源，也和上面的红线不矛盾：**幽默可以有，但只能长在真实发生的事情上，不能为了搞笑去编一个没发生的坑。** 判据是——删掉这句玩笑，底下那条技术事实（真花的时间、真踩的坑、题目的真实性质、真实的难度落差）依然站得住。

真实幽默的常见手法（都建立在事实之上）：

- 自嘲真实代价：“新手题做了一整天，榜上的师傅几小时就切了，我不是那种师傅。”——前提是你确实卡了这么久。
- 干冷吐槽题目真实性质：“这个 SSTI 过滤约等于没有，绕过方式比我分多。”“出题人还挺善良，waf 提示都写脸上了。”——评价的是题目客观特征。
- 顺着题目主题玩梗：题目叫 White Rabbit 就顺着“follow the rabbit”写，题目全是原题就吐槽“osint 把取证夺舍了”。
- 结尾专门复盘真实弯路（“踩坑/Mistakes”小节）：老实列出走错的方向和它为什么错（“一直往栈溢出想，其实是把 pwn 当成 RE 在做”），这是最受欢迎也最像人的收尾，且信息量很高。
- 带梗但仍准确的小节标题：“要、要溢出来了”“NC？启动！”——标题有个性，内容照样交代清楚。

不要做的：

- 不为幽默牺牲准确或可复现。玩笑之外，命令、偏移、payload 该精确还是精确；读者能照着跑通永远是第一位。
- 不硬凑。憋不出来就写平实准确的句子——一句诚实的陈述胜过一个尬笑话。幽默是诚实叙述的副产品，不是刷在表面的漆。
- 不越过红线：吐槽“我卡了一天”必须是真卡了一天；复盘的弯路必须真走过。假装的犹豫、编造的弯路、无中生有的时间线，被检测器和评委抓到比“像 AI”更糟。
- 注意场合与密度：给主办方的正式提交、公开题解口吻收着点，队内归档和个人博客可以更放开；无论哪种，一篇里几处点到为止即可，通篇玩梗会盖掉技术信息，也显得刻意。

一句话：让文章好笑的不是段子，是你如实写出的真实经历本身自带的反差和取舍。

## 各题型应保留的证据

### Web / API

- 一组正常请求与触发请求的关键差异。
- 路由、参数、身份/会话状态和后端决定性分支。
- payload、完整请求方式、关键响应及其解释。

### Pwn / Native

- 文件哈希、架构、保护、loader/libc 和协议帧。
- 崩溃偏移、泄漏来源、基址计算、原语与目标对象。
- 本地/远程差异、最终 Exp 调用和成功检查点。

### Reverse / Mobile

- 样本哈希、入口、关键函数/地址、数据流和加载时机。
- 关键反编译片段或动态 hook 结果，以及它们如何相互验证。
- 提取、patch、模拟或算法还原步骤及派生产物。

### Crypto

- 输入的精确编码、字节序、参数、公式和攻击成立条件。
- 推导中的关键中间值、边界/精度/种子，以及重加密或已知向量验证。
- 完整 solver 和候选明文到 Flag 的解析方式。

### Forensics / Misc / OSINT

- 原件哈希、元数据、时区、提取/解码链和派生产物路径。
- 时间线或来源之间的关联方式，以及排除诱饵/误报的反证。
- 外部来源的访问日期与交叉验证；不收集题目目标外的个人信息。

## AI 使用说明

说明应匹配实际分工，不使用统一话术弱化实质性参与。可按以下三项组织成一到三句：

1. AI 做了什么：例如整理记录、解释反编译、提出攻击条件、推导算法、生成/调试代码或润色结构。
2. 作者做了什么：例如定位入口、执行命令、调试 payload、核对公式或复现远程请求。
3. 如何验证：指出关键命令、脚本或附件结果。

### 描述“协助模式”

很多比赛更认可“人主导、AI 作对话式顾问”的解题方式，对“交给自动化代理全程执行”存在偏见。如果实际工作方式确实是人在环里主导——由作者判断方向、亲自执行命令、逐步核对结果，AI 只在对话中提供思路、解释代码或推导——那么如实写成“对话式/顾问式 AI 辅助”既准确又符合这一偏好。要让这句话站得住，解题过程就应真实反映作者的决策、执行和验证动作（见 `references/ctf/writeup/index.md` 的自然写作规范）。

不要为了迎合这种偏好而谎报协助模式：若实际由自动化流程独立完成关键分析，不要声称是纯对话辅助。准确的做法是既写清 AI 的实质贡献，也写清作者亲自完成和复核了哪些环节——这比含糊其辞更能通过复核。

仅协助整理时可写：

```text
本题由作者主导分析与调试，AI 仅在对话中协助梳理记录、调整表述；漏洞定位、脚本运行与 Flag 校验均依据文中保存的命令和输出，由作者执行核对。
```

AI 参与实质分析或代码时应明确写出，例如：

```text
本题使用 AI 在对话中协助分析校验逻辑、推导利用条件并给出 solver 初稿；作者据反编译结果修正参数，在题目环境中运行脚本并核对最终 Flag。
```

若实际分工不同，重新表述，不要照抄示例。

## 缺失信息处理

- 只有 Flag：输出信息缺口清单和六段草稿骨架，不生成虚构过程。
- 只有最终脚本：可以解释脚本中可直接证明的算法与数据流，但不能反推作者当时如何发现它。
- 只有 AI 输出：先用题目附件或运行环境验证其中的关键事实；未验证内容标为候选。
- 命令有记录但输出缺失：保留命令并标明输出未保存，不编造“预期输出”作为实际结果。
- 题目尚未完全解出：标题和状态明确写为阶段记录，不填最终 Flag，不宣称完整 WriteUp。

## 完成检查

- [ ] 六个必需部分齐全，或缺失项有真实原因。
- [ ] 题目信息里有一句话打法，读者不看正文也能明白整条链。
- [ ] 最终 Flag 的来源、格式和唯一性已验证。
- [ ] 题目分析说明机制，解题思路说明路线选择，解题过程展示实际证据；三者没有互相复制。
- [ ] 每个关键命令、请求、偏移、公式和输出都能追溯到记录或产物。
- [ ] 代码完整可运行，并写明依赖、调用和预期检查点。
- [ ] 失败尝试只包含实际发生且有助于理解转折的内容。
- [ ] 没有占位符、虚构经历、题目外秘密或无关长日志。
- [ ] AI 使用说明准确覆盖实质性参与和验证方式。
- [ ] 另一名队友可以仅凭 WriteUp 与题目材料复现关键路径。
